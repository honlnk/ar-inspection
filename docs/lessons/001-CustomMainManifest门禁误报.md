# 复盘 001：Custom Main Manifest 门禁误报

- 日期：2026-10-27
- 影响范围：计划 001（三端工程骨架搭建）的 Unity 阶段验收结论，以及向用户交付的操作指引
- 一句话结论：工程配置从一开始就是正确的；错误出在验收脚本用了一个与开关无关的序列化字段做判定，把「已启用」误报成「未启用」，进而推导出错误的「需手动勾选」结论。

## 1. 背景

Unity 工程需要一份自定义 Android Manifest，用于声明：

1. `INTERNET` 权限——手机访问电脑上的 Go 后端必需；
2. `com.google.ar.core` 的包可见性声明——Android 11+ 侧载应用查询 ARCore 可用性必需，缺失时运行时报 `UNKNOWN_ERROR`（真机验证阶段实测踩过）。

这份文件已按 Unity 约定放在标准路径 `Assets/Plugins/Android/AndroidManifest.xml`。骨架验收脚本（阶段门禁自检）需要验证「Custom Main Manifest 已启用」。

## 2. 现象与矛盾

用户首次用编辑器打开工程后反馈：Player Settings → Publishing Settings 里的 Custom Main Manifest **本来就是勾选状态**，且指向上述标准路径文件。这与当时的验收结论矛盾：

| 证据 | 当时验收脚本的判断 |
| --- | --- |
| 编辑器 UI：开关已勾选，路径正确 | 读取 `ProjectSettings.asset` 中的 `useCustomMainManifest` 字段，值为 `0`，判定 FAIL |
| 标准路径 Manifest 文件存在，内容完整 | 由此推断「开关未启用，需用户在 GUI 手动勾选一次」 |

UI 状态与磁盘字段不一致，说明两者根本不是同一个状态源——当时没有识别这一点，直接相信了字段。

## 3. 开关的真实机制

联网查证与本机验证得到的一致结论：

1. **这个开关由文件是否存在决定，没有公开的读写 API。** Unity 员工在官方论坛明确说明：UI 开关「按文件是否存在工作」，程序化启停的做法是重命名文件（取消勾选时 Unity 会把 `AndroidManifest.xml` 重命名为 `.DISABLED`）。
2. **本机 Unity 6000.3.27f1 的 Android 模块同样实现了这套机制**：模块内包含 `.DISABLED` 重命名逻辑，以及「模板文件与禁用模板文件不得同时存在」的校验文案。
3. **`ProjectSettings.asset` 中的 `useCustomMainManifest` 字段不是这个开关状态的来源。** 它是历史遗留的序列化字段，写它不会改变开关，读它也代表不了开关。

因此：Manifest 文件放进标准路径的那一刻，开关就已经启用。用户看到的勾选状态是正确且预期的。

## 4. 误判是如何形成的

| 环节 | 当时的判断 | 错在哪里 |
| --- | --- | --- |
| 初始化脚本写入序列化字段 | 写入成功、无报错，认为开关已启用 | 该字段不驱动开关，写入是无效操作 |
| 验收脚本复读该字段 | 值为 `0`，认为开关未启用 | 判定依据与真实机制不同源 |
| 搜索全部编辑器 DLL 找不到开关 API | 推断「无 API，所以只能 GUI 手动勾选」 | 「无 API」只能推出「不能程序化设置」，推不出「必须人工操作」——文件本身就能启用开关 |
| GUI 写入字段被还原 | 归因于「内部状态还原，GUI 独占」 | 现象真实，但归因错了：字段本来就不是开关状态，写不写都不会变 |

根因归纳为两条：

1. **判定依据与被验证机制不同源**——用序列化字段去验证一个由文件存在性驱动的开关；
2. **从「无 API」越界推出「需人工」**——缺少对启用机制本身的查证。

## 5. 修复与验证

修复内容：

1. 初始化脚本删除对该序列化字段的无效写入；
2. 门禁自检改为检查标准路径 Manifest 文件存在及其内容（`INTERNET` 权限 + ARCore 包可见性声明）；
3. 计划 001 状态与验收结论、README、AI_LOG 同步勘误。

验证过程（在用户已打开的编辑器中）：

1. 修复脚本后首次运行菜单自检，跑到的仍是未刷新的旧程序集，复现旧 FAIL——不采信；
2. 执行 Assets → Refresh，脚本重新编译，无错误；
3. 再次运行菜单「现场巡检 / 阶段门禁自检」，24 项检查全部 PASS。

检查项数量从 25 变为 24 的原因：删掉的是那条错误检查本身，不是把它改成通过。剩余 24 项均为有效检查。

## 6. 影响评估

- 工程：无需返工，Manifest 文件与开关状态一直正确；
- 用户：被误导多跑了一趟 Project Settings，浪费了时间；
- 文档：计划 001 一度把 SK-02 标为「24/25、需手动勾选」，README 也写入过同一路径的手动步骤，均已勘误（计划文档保留原始错误记录与追记四勘误，不抹改历史）；
- 后续：Android 构建产物中的最终合并 Manifest 仍需在首次构建时验证，这与本误报无关，属既定后续计划。

## 7. 防再犯规则

1. **判定依据必须与机制同源**：验证一个开关前，先弄清它的状态存在哪里（文件、资产、序列化字段还是编辑器内部状态），再决定读什么。
2. **「无 API」不等于「只能人工」**：无公开 API 只说明不能程序化设置，还可能存在约定式机制（如标准路径文件自动生效），需单独查证。
3. **UI 与底层字段矛盾时优先怀疑映射关系**，不要默认 UI 显示的是所读字段的值。
4. **外部修改 Unity 脚本后必须触发资产刷新再验证**，否则菜单执行的可能是旧程序集，新旧结果要按日志区分。
