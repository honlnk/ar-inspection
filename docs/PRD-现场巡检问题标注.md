# 现场巡检问题标注 PRD（草案）

> 文档状态：已确认，作为首版必做需求基线
> 需求来源：`docs/Unity-AR研发实操题-候选人任务书-简略版.md`
> 编写日期：2026-10-26
> 适用范围：本作业的必做功能、数据约定、验收与交付要求

## 1. 背景

园区巡检人员发现墙面破损、设备异常或安全隐患时，需要用手机在问题现场放置 AR 标记并上报。管理人员随后在电脑网页中查看问题，并更新处理状态。

本产品的目标是完成一个可运行、可验证的小型原型，打通真机 AR 上报、后端保存和网页处理的完整流程。首版以基础功能和稳定闭环为主，不追求复杂架构、精美界面或美术效果。

## 2. 产品目标

1. 巡检人员能在支持 AR 的真机上检测真实水平平面，并在平面上放置标记。
2. 巡检人员能提交包含标题、描述、优先级和标记位置的问题，并获知提交结果。
3. Go 后端能保存问题、返回列表、修改状态，并在重启后保留数据。
4. 管理人员能在 React 页面查看同一批问题并修改处理状态。
5. 三端使用一致的字段和枚举，Unity 与 React 共用同一个 Go 后端及同一份数据。
6. 最终交付能够按照任务书完成真机和电脑端演示，并如实记录 AI 使用过程及已知问题。

## 3. 用户与使用场景

| 用户 | 使用端 | 核心任务 |
| --- | --- | --- |
| 园区巡检人员 | Unity AR 移动端 | 在现场放置标记并上报问题 |
| 管理人员 | React 管理端 | 查看问题并更新处理状态 |

典型场景：巡检人员发现“入口墙面破损”，将手机摄像头对准真实水平平面，点击平面放置标记，填写问题标题、描述和优先级后提交。管理人员刷新电脑网页，看到该问题，并根据处理进展更新其状态。

## 4. 范围与约束

### 4.1 首版范围

首版仅承诺完成任务书规定的以下能力：

- Unity 真机 AR 平面检测、标记放置和问题上报；
- Go 服务状态检查、问题保存与查询、状态修改、参数校验和数据持久化；
- React 问题列表、状态修改和后端异常提示；
- 三端统一的数据结构；
- README、AI 使用记录和演示视频等交付材料。

### 4.2 技术与运行约束

| 部分 | 要求 |
| --- | --- |
| 移动端 | Unity LTS、C#、AR Foundation；本项目采用 Android + ARCore 路线 |
| 管理端 | React、TypeScript |
| 后端 | Go，框架不限 |
| 持久化 | SQLite 本地文件；满足任务书允许的持久化方式，架构决策详见架构文档 |
| AR 设备 | 支持 AR 的真机，不以普通 3D 场景或屏幕固定物体替代真实 AR |
| 数据来源 | Unity 和 React 必须连接同一个 Go 后端，使用同一份持久化数据 |
| 浏览器访问 | React 在浏览器中能够正常访问 Go 后端 |
| AI 使用 | 可以使用 AI 辅助开发，但产品本身不要求接入大模型 |

现有真机为 iQOO Z9（V2361A，Android 16）。ARCore 运行时 1.57.0 的支持状态、会话创建、相机启动和运动跟踪已完成前置验证；Unity 中的水平平面检测、标记放置和完整上报流程仍需在开发完成后验收。

### 4.3 不属于首版必做范围

以下内容不是本次基础交付的强制要求，不应影响必做闭环的完成：

- 应用重启后，将历史标记恢复到完全相同的真实物理位置；
- 精美 UI、复杂美术资源或复杂系统架构；
- 强制提供 APK 或部署到公网；
- 在产品中接入大模型；
- 登录、权限、人员管理、筛选、详情、删除、历史问题编辑、WebSocket、Docker、自动化测试等加分功能。

加分项只有在必做功能完成并稳定后才考虑，且需要另行确认，不因列入任务书的参考方向而自动进入本 PRD。

## 5. 核心业务流程

1. 巡检人员在真机上启动 Unity AR 应用，并检测真实环境中的水平平面。
2. 巡检人员点击已检测到的平面，系统在命中位置放置一个简单标记。
3. 巡检人员填写标题、可选描述和优先级，系统随标记的 x/y/z 坐标一起提交问题。
4. Go 后端校验并保存问题，生成唯一 ID、默认 `open` 状态及后端时间字段。
5. 移动端明确显示提交成功或失败。
6. 管理人员在 React 页面获取并查看问题列表；刷新后能够看到新上报的问题。
7. 管理人员将问题状态修改为 `open`、`in_progress` 或 `resolved`，后端保存修改结果。
8. Go 服务重启后，已保存的问题及其处理状态仍然存在。

## 6. 功能需求

### 6.1 Unity AR 移动端

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| AR-01 | 在支持 AR 的真机上运行 | 应用能在真机启动，并使用真实 AR 能力完成后续流程 |
| AR-02 | 检测真实环境中的水平平面 | 能识别真实水平平面，并以其作为标记放置依据 |
| AR-03 | 点击平面放置标记 | 点击已检测平面后，在命中位置出现立方体、球体等简单标记 |
| AR-04 | 记录标记位置 | 上报时包含该标记的 `position.x`、`position.y`、`position.z` |
| AR-05 | 填写并提交问题 | 支持填写必填标题、可选描述及 `low/medium/high` 优先级 |
| AR-06 | 提示提交结果 | 提交成功和提交失败均有用户可感知的明确提示 |
| AR-07 | 防止 UI 误触放置 | 点击按钮或输入框时，不会在 AR 场景中误放标记 |

标记样式不作为美术验收项，但必须能证明标记位于真实 AR 平面的命中位置，而不是固定在屏幕上。

### 6.2 Go 后端

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| API-01 | 提供服务运行状态检查 | 可通过接口确认服务是否正常运行 |
| API-02 | 接收并保存问题 | 能接收 Unity 上报的数据，并保存到持久化存储 |
| API-03 | 返回问题列表 | 能返回已经保存的问题，供 React 获取和展示 |
| API-04 | 根据 ID 修改状态 | 能按问题 ID 将状态改为三种合法状态之一 |
| API-05 | 生成服务端字段 | 为新问题生成唯一 ID，并生成 `createdAt`、`updatedAt` |
| API-06 | 设置默认状态 | 新问题的默认 `status` 为 `open` |
| API-07 | 校验参数 | 标题为空或枚举值非法时，请求不被当作有效数据保存，并返回明确的参数错误 |
| API-08 | 重启后保留数据 | Go 服务停止并重新启动后，重启前的问题和状态仍可查询 |
| API-09 | 共用同一份数据 | Unity 上报的问题可被 React 查询，React 的状态修改作用于同一条后端数据 |
| API-10 | 支持浏览器访问 | React 页面在浏览器中可正常调用后端接口，不被访问配置阻断 |

接口路径、请求方法、响应外层格式和具体错误码可以自行设计，但必须在 README 中简要说明，且不能削弱上述行为和字段约定。

### 6.3 React 管理端

| 编号 | 需求 | 验收口径 |
| --- | --- | --- |
| WEB-01 | 获取问题列表 | 页面从 Go 后端获取已经保存的问题 |
| WEB-02 | 展示核心信息 | 列表至少展示每条问题的标题、优先级和状态 |
| WEB-03 | 修改处理状态 | 能将问题状态修改为 `open`、`in_progress` 或 `resolved` |
| WEB-04 | 显示修改结果 | 状态修改成功后，页面展示对应问题的新状态 |
| WEB-05 | 处理后端不可用 | 后端不可用时页面显示错误提示，不能出现无说明的白屏 |

## 7. 数据需求

### 7.1 统一数据结构

三端字段名称保持一致：

```json
{
  "id": "由后端生成",
  "title": "入口墙面破损",
  "description": "左侧墙体存在裂缝",
  "priority": "high",
  "status": "open",
  "position": {
    "x": 0.42,
    "y": 0.03,
    "z": 1.26
  },
  "createdAt": "由后端生成",
  "updatedAt": "由后端生成"
}
```

| 字段 | 来源与约束 | 含义 |
| --- | --- | --- |
| `id` | 后端生成，唯一 | 问题标识，用于查询对应数据和修改状态 |
| `title` | 巡检人员填写，必填，不能为空 | 问题标题 |
| `description` | 巡检人员填写，可选 | 问题描述 |
| `priority` | 仅限 `low`、`medium`、`high` | 问题优先级 |
| `status` | 仅限 `open`、`in_progress`、`resolved`；新建默认为 `open` | 处理状态 |
| `position` | Unity 根据标记位置提供 | AR 标记的三维坐标 |
| `position.x` | 数值 | 标记 x 坐标 |
| `position.y` | 数值 | 标记 y 坐标 |
| `position.z` | 数值 | 标记 z 坐标 |
| `createdAt` | 后端生成 | 创建时间 |
| `updatedAt` | 后端生成 | 更新时间 |

时间字段的具体格式由后续接口设计确定，但三端不得改变字段名称。

### 7.2 枚举值

| 枚举 | 合法值 |
| --- | --- |
| 优先级 | `low`、`medium`、`high` |
| 处理状态 | `open`、`in_progress`、`resolved` |

任务书未要求限制三种处理状态之间的转换顺序，首版不额外增加状态流转限制。

### 7.3 持久化与一致性

- 问题数据必须存入 SQLite 或本地 JSON 文件，不能只保存在内存中。
- Go 服务重启不能清空已保存的问题或状态。
- Unity 和 React 不得分别使用互不相通的数据副本。
- 应用重启后不强制恢复历史标记的真实物理位置，但这不免除后端问题数据的持久化要求。

## 8. 异常与边界要求

| 场景 | 产品要求 |
| --- | --- |
| 上报标题为空 | 后端返回明确的参数错误，不保存为有效问题 |
| 上报优先级非法 | 后端返回明确的参数错误 |
| 状态修改值非法 | 后端返回明确的参数错误 |
| Unity 提交失败 | 移动端明确提示失败，不把失败表现为成功 |
| React 请求时后端不可用 | 页面显示错误提示，保持可理解、可操作的界面，不白屏 |
| 点击 Unity 按钮或输入框 | 只执行对应 UI 交互，不触发 AR 标记放置 |
| Go 服务重启 | 重启前的数据仍可获取，React 修改过的状态不回退 |

## 9. 验收场景

以下场景全部通过后，才视为必做功能闭环完成：

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 真机 AR 放置 | 真机识别真实水平平面，点击后在命中位置出现简单 AR 标记 |

| AC-04 | 必填与枚举校验 | 空标题和非法枚举均收到明确参数错误，不产生有效问题数据 |
| AC-05 | 上报失败提示 | 模拟提交失败后，移动端有明确失败提示 |
| AC-06 | 网页查看新数据 | React 从后端获取列表，刷新后能看到刚上报的问题及标题、优先级、状态 |
| AC-07 | 网页修改状态 | 能将问题修改为三种合法状态，修改后页面与后端数据一致 |
| AC-08 | 后端异常提示 | Go 后端不可用时，React 显示错误而非白屏 |

| AC-10 | 重启持久化 | 重启 Go 服务后，问题及修改后的状态仍存在 |
| AC-11 | 三端字段一致 | 实际请求和响应使用统一字段及枚举，ID 和时间字段由后端生成 |

## 10. 交付要求

### 10.1 源码与文档

- 提交 Unity、React、Go 的完整源码。
- 提交简短 README，说明实际使用的版本、三端启动方式、Unity 真机后端地址配置，以及已完成、未完成和已知问题。
- README 简要说明后端接口路径和响应格式。
- 提交 AI_LOG，按实际顺序保留所有主动发送给 AI 的 Prompt 原文和结果，包括追问、纠错及验证方式。
- AI_LOG 至少包含一次检查、修改或放弃 AI 结果的过程。
- 不提交 API Key、Token、账号、个人隐私或其他敏感信息；必要内容使用 `[REDACTED: …]` 脱敏。
- 候选人需要能够解释最终提交的核心代码。

### 10.2 演示视频

提交手机和电脑两段视频，每段 3～5 分钟。两段视频合起来至少展示：

1. 真机识别平面并放置标记；
2. 手机提交问题；
3. React 刷新后看到该问题；
4. React 修改状态；
5. Go 重启后数据仍然存在。

### 10.3 分享方式

可通过 GitHub、Gitee、百度网盘或其他无需特殊权限、能够正常下载的方式分享全部交付内容，并提供访问链接。如有访问权限、提取码或有效期，需要一并说明，并保证评审期间可访问。

使用 GitHub 或 Gitee 时必须保留完整 Git 历史；使用网盘等方式时，将源码、文档和演示视频整理后统一上传。

## 11. 质量评价重点

1. 是否完成真实 AR，而非普通 3D 场景或屏幕固定物体。
2. Unity、React、Go 是否形成可运行的最小闭环。
3. 遇到问题时是否能够定位、修正并验证。
4. 是否合理使用 AI，并能解释最终核心代码。
5. 是否如实说明未完成内容和已知问题。

## 12. 技术设计引用与后续计划

PRD 规定“做什么”，具体技术实现以 `docs/ARCHITECTURE-现场巡检问题标注.md` 为准。当前已确定：

- 持久化采用 SQLite 本地文件；
- Go 使用 Gin，API 路径、响应结构和错误码见架构文档；
- Unity、React 的技术栈、界面参考和后端地址配置方式见架构文档；
- 业务时间采用北京时间，UTC+08:00。

工程创建时仍需确认 Unity 和配套依赖的精确版本，并同步到 README。开发阶段划分和加分项不属于本 PRD；首版先完成必做内容，后续另行制定开发计划。
