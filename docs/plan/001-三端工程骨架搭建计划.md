## 1. 计划目标

本计划是三端业务开发前的第一个施工计划，目标是把仓库中的三个占位目录变成结构明确、依赖可复现、能够分别启动和编译的工程，为后续 AR 上报、问题列表和状态修改提供稳定基础。

本期完成后的标准不是“产品已经能用”，而是：

1. Unity 工程可以由指定 LTS 编辑器正常打开，AR 与 Android 构建所需配置已经落地。
2. Go 服务可以启动，能够初始化 SQLite，并通过健康检查确认服务与存储可用。
3. React 工程可以启动并显示静态管理台外壳，TypeScript 检查和生产构建通过。
4. 三端目录、配置、依赖锁文件和 README 相互一致，后续施工不需要重新搭建工程。
5. 不把骨架验收冒充为 AR 平面检测、三端数据闭环或产品功能验收。

## 2. 本期边界

| 部分 | 本期交付 |

- 不实现真机平面检测、射线命中、标记放置、相机交互或 UI 防误触。
- 不实现 Unity 问题表单、网络上报、成功/失败业务提示或 PlayerPrefs 后端地址界面。
- 不实现问题创建、完整问题列表业务接口、状态修改及参数校验的完整业务逻辑。
- 不实现 React 真实数据加载、刷新、状态保存、加载反馈、错误重试或空列表业务状态。
- 不实现登录、筛选、详情、删除、分页、WebSocket、历史标记恢复等加分项。
- 不录制正式演示视频，不部署公网，不制作或强制交付 APK。
- 不修改 `tools/ar-support-check/`，不修改 `../linkseek`，不创建或使用 MySQL 容器。
- 不为了展示“骨架完成”而加入模拟问题数据或伪造三端联调成功。

## 3. 已锁定的实施决策

以下事项在本计划中直接确定，不留给施工方重新选择：

| 决策项 | 本期执行口径 |

| 接口基础 | 统一使用 `{ "data": ... }` 与 `{ "error": { "code": "...", "message": "..." } }` 结构；本期只开放健康检查 |
| 数据契约 | 三端预留完全一致的字段名和枚举，不建立生成代码或共享包 |
| 环境配置 | 提交无敏感信息的 `.env.example` 或等价示例；本地覆盖值和本地数据库不提交 |
| 远程操作 | 不 push、不创建 PR，不改变现有 Git 历史 |

### 阶段 1：Go 后端骨架

施工内容：

1. 初始化 Go Module，引入并锁定 Gin 和 `modernc.org/sqlite`。
2. 按模型、存储、HTTP 三层建立文件，不让 HTTP 层直接拼接 SQL。
3. 建立 `issues` 单表和 `(created_at DESC, id)` 查询索引，字段与架构文档一致。
4. 启动时创建数据库目录、打开 SQLite、执行建表和轻量检查；失败时打印明确错误并退出，不降级为内存存储。
5. 默认监听 `:8080`，默认数据库为 `./data/inspection.db`。
6. 实现 `GET /api/health`：服务与存储都可用时返回 `200` 和 `data.status = ok`；存储检查失败返回 `503 service_unavailable`。
7. 建立统一 JSON 响应、未知路由错误和 CORS 基础配置；预检支持 `GET/POST/PATCH/OPTIONS`。
8. 为健康检查、空数据库初始化和存储重连建立最小 Go 测试。完整创建/改状态接口测试留给对应业务计划。
9. 验证后使用临时数据库测试，不把测试数据写入交付文档或 Git。

阶段门禁：

```bash
cd backend
gofmt -w cmd internal
go test ./...
go build ./cmd/server
go run ./cmd/server
```

- 所有测试、编译和格式化检查通过。
- 另开终端请求 `http://localhost:8080/api/health`，返回 `200` 和统一成功结构。
- 全新临时数据库能自动建表；停止并重启服务后仍能健康启动。
- 健康检查不是仅返回进程存活，而是实际执行 SQLite 轻量检查。
