## 1. 计划目标

在计划 001 已完成的工程骨架上，把 Go 后端从“可启动、可初始化存储”推进为“可独立完成问题数据闭环”的服务。

本期结束时，不依赖 Unity 或 React，仅通过真实 HTTP 请求就应能完成：

1. 创建一条包含标题、描述、优先级和三维位置的问题。
2. 从列表中查询到该问题及后端生成的完整字段。
3. 根据 ID 修改处理状态并获取服务端最新结果。
4. 停止并重启 Go 服务后，问题和修改后的状态仍然存在。
5. 非法输入、资源不存在和存储故障均返回符合契约的错误，不产生虚假成功。

本期验收的是后端独立业务闭环，不代表真机 AR、Unity 上报、React 操作或三端联调已经完成。

## 4. 已锁定的业务与接口规则

以下规则直接执行，不留“任选其一”：

| 决策项 | 本期规则 |
| --- | --- |
| 客户端创建字段 | 仅接受 `title/description/priority/position`；省略 `description` 时保存为空字符串 |
| 标题 | 使用 Go 字符串首尾空白清理后校验并保存清理后的标题；清理后不能为空 |
| 描述 | 保持用户输入内容，不强制 trim；省略时为空字符串 |
| 优先级 | 精确匹配小写 `low/medium/high`，不做大小写转换或别名兼容 |
| 位置 | `position` 及其 `x/y/z` 必须存在且为数值；零和负数合法；NaN、正负无穷非法 |
| 未知字段 | 创建和状态修改请求一律拒绝，包括客户端传入 ID、状态或服务端时间 |
| JSON 请求体 | 必须是单个完整 JSON 对象，拒绝语法错误、字段类型错误及对象后的额外非空白内容 |
| 请求体上限 | HTTP 层限制为 1 MiB；超限返回 `400 invalid_argument`，不读取无限请求体 |
| 新建状态 | 固定为 `open`，客户端不能指定 |
| ID | 使用 `crypto/rand` 生成 UUID 格式字符串；生成失败返回服务器错误，不降级为可预测 ID |
| 新建时间 | 后端使用固定 UTC+08:00 生成 RFC 3339 字符串，初始 `createdAt == updatedAt` |
| 状态转换 | 三种状态可以任意直接转换，不限制工作流顺序 |
| 重复设置同一状态 | 视为合法更新，返回 `200`，并重新生成 `updatedAt`；其他字段不变 |
| 校验与查找顺序 | 先校验 JSON 和状态值，再查询 ID；因此不存在 ID 配合非法状态时返回 `400` |
| 状态更新时间 | 成功更新时生成新的北京时间；保留 `id/title/description/priority/position/createdAt` |
| 时间精度 | 对外采用 RFC 3339 秒级格式；同一秒内的合法更新允许时间字符串相同，不伪造递增时间 |
| 列表顺序 | `createdAt DESC`；相同时间按 `id ASC`；首版返回全部记录 |
| 空列表 | 返回 `{ "data": [] }`，不返回 `null`，不把它当作错误 |
| 写入成功条件 | SQLite 事务提交成功后才返回成功；响应优先读取并返回提交后的完整记录 |
| SQL | 全部使用参数化 SQL，不拼接用户输入或 ID |
| 错误信息 | HTTP 状态与错误码按架构文档执行；`message` 为明确中文，不包含 SQL、堆栈、本机路径或内部连接串 |

## 5. 接口契约与验收样例

### 5.1 创建问题

请求：`POST /api/issues`，`Content-Type: application/json`。

```json
{
  "title": "入口墙面破损",
  "description": "左侧墙体存在裂缝",
  "priority": "high",
  "position": { "x": 0.42, "y": 0.03, "z": 1.26 }
}
```

成功结果：

- HTTP `201`。
- 响应为 `{ "data": Issue }`。
- `id` 为非空 UUID，`status` 为 `open`。
- `createdAt` 和 `updatedAt` 为带 `+08:00` 的 RFC 3339 字符串且初始相同。
- 标题、描述、优先级和位置与有效输入一致。
- 随后查询列表和重启服务后仍能读取同一 ID。

### 5.2 查询列表

请求：`GET /api/issues`。

成功结果：

- HTTP `200`，`data` 始终为数组。
- 每条记录字段严格为 `id/title/description/priority/status/position/createdAt/updatedAt`。
- `position` 只包含 `x/y/z`，数据库蛇形列名不得泄露到 JSON。
- 排序符合第 4 节；存储层相同时间测试通过注入 ID 与创建时间验证，不依赖真实时间恰好相同。

### 5.3 修改状态

请求：`PATCH /api/issues/{id}/status`。

```json
{
  "status": "in_progress"
}
```

成功结果：

- HTTP `200`，返回更新后的完整问题。
- 状态和 `updatedAt` 来自服务端，其他业务字段及 `createdAt` 不变。
- 再次查询列表显示相同结果。
- 不存在的合法 ID 返回 `404 issue_not_found`；空 ID、畸形路径由路由统一处理，不新增兼容别名。

### 5.4 错误响应

| HTTP 状态 | 错误码 | 本期场景 |
| --- | --- | --- |
| `400` | `invalid_argument` | JSON 无法解析、额外 JSON 内容、请求体过大、字段缺失或类型错误、未知字段、空标题、非法枚举、无效坐标 |
| `404` | `issue_not_found` | 状态修改对应的问题 ID 不存在 |
| `404` | `not_found` | API 路径不存在 |
| `405` | `method_not_allowed` | 已知路径使用未开放的方法 |
| `500` | `internal_error` | ID 或时间生成失败、事务、查询、扫描或提交等内部失败 |
| `503` | `service_unavailable` | 健康检查发现存储不可用 |

错误响应不得同时包含 `data`，成功响应不得同时包含 `error`。内部详细错误仅写本机日志。

## 6. 分阶段施工与门禁

### 阶段 1：模型、校验与服务端字段

施工内容：

1. 对照现有模型，定义创建请求、状态修改请求和完整 Issue 响应结构；必须区分数值零值与缺失字段。
2. 集中实现标题、优先级、状态、位置、未知字段和完整 JSON 对象校验，HTTP 与存储共用同一领域约束。
3. 实现 UUID 和固定 UTC+08:00 时间生成；通过可替换的小函数或时钟便于测试失败路径，不引入通用依赖注入框架。
4. 新建问题由领域逻辑统一设置 ID、默认状态和时间，HTTP 层不自行拼装一套服务端字段。
5. 增加表驱动测试，覆盖合法边界、空值、类型、枚举、未知字段和 NaN/无穷值；标准 JSON 无法表达的非有限数在模型/存储校验测试中直接构造。

阶段门禁：

- 模型和校验测试全部通过。
- `0`、负数坐标被接受；缺失坐标与非有限数被拒绝。
- 创建请求无法覆盖 ID、默认状态和时间。
- 时间可解析为 RFC 3339 且偏移为 `+08:00`。

### 阶段 2：SQLite 业务读写与持久化

施工内容：

1. 在现有存储实现中补齐创建、列表和按 ID 更新状态，不建立内存副本。
2. 创建与更新使用事务和参数化 SQL；事务失败完整回滚，提交失败不能返回成功。
3. 映射嵌套 Position 与蛇形数据库列；查询时初始化空切片，保证空列表序列化为 `[]`。
4. 按 `created_at DESC, id ASC` 查询，核对现有索引与该顺序匹配；需要调整时使用幂等索引语句，不删除业务表。
5. 根据已锁定 SQLite 驱动的实际文档核对连接数、外键以外的表约束、busy timeout 和 WAL 配置，只记录真实生效的参数，不虚构配置。
6. 增加存储测试：创建后读取、空列表、三种状态、重复状态、不存在 ID、稳定排序、约束防御、关闭并重新打开同一文件后的持久化。
7. 通过受控故障或测试替身验证事务/存储失败不会留下部分成功结果；不通过损坏正式数据库制造故障。

阶段门禁：

- 存储测试和 `go test -race ./internal/issue/...` 通过。
- 同一数据库重连后，问题及最后状态不丢失。
- 写入失败没有新增有效记录或部分字段更新。
- SQL 注入样式字符串作为标题时仅作为普通文本保存，不改变查询结构。

### 阶段 3：HTTP 业务接口与统一错误

施工内容：

1. 在现有 Gin 路由和统一响应基础上开放三个业务接口，不增加重复路由。
2. 创建与状态修改使用严格 JSON 解码，限制 1 MiB 请求体，拒绝未知字段和额外 JSON 内容。
3. 将参数错误、问题不存在和内部错误映射到第 5.4 节，不向客户端暴露内部错误细节。
4. 列表查询失败返回 `500 internal_error`，不能返回空数组伪装成功。
5. 保留并验证健康检查、CORS、`404 not_found` 和 `405 method_not_allowed`；CORS 允许已配置的 Web Origin、JSON 请求头及 `GET/POST/PATCH/OPTIONS`。
6. 使用 `httptest` 覆盖 HTTP 状态、响应字段、中文错误结构、请求头、预检及故障路径；存储故障通过接口替身或受控关闭测试存储注入。
7. 创建成功后使用响应中的 ID 继续调用状态接口和列表接口，验证后端内部链路使用同一条记录。

阶段门禁：

- 全部 HTTP 测试通过，成功与错误结构互斥。
- 创建返回 `201`，列表和状态修改返回 `200`，错误码与契约一致。
- 浏览器预检返回 `204` 且包含 `Vary: Origin`；未配置 Origin 不被放行。
- 服务器错误响应不包含 SQL、文件路径或堆栈。

### 阶段 4：真实进程与重启验收

施工内容：

1. 在独立临时目录创建验收数据库，使用非默认测试端口启动真实 `go run ./cmd/server` 或已编译服务，避免影响其他会话正在使用的进程。
2. 请求健康检查，依次创建至少三条覆盖三种优先级的问题，确认 UUID 不重复、默认状态和位置正确。
3. 查询列表，核对完整字段、空值和排序；对其中一条依次设置 `in_progress`、`resolved`、`open`，验证任意状态转换。
4. 使用 `curl` 执行空标题、非法枚举、未知字段、额外 JSON、错误类型、不存在 ID 等负例，并确认问题总数没有因非法请求增加。
5. 正常停止该测试服务，使用同一临时数据库重新启动，再次查询并核对 ID、状态和 `createdAt`；再执行健康检查。
6. 验证停止服务后客户端请求表现为连接失败，而不是由测试脚本伪造成功；Unity/React 的提示界面不在本期验收。
7. 清理自己创建的临时进程和文件，不终止其他进程，不删除正式数据库。

## 9. 风险、降级与偏差处理

| 情况 | 处理方式 |
| --- | --- |
| 计划 001 实际尚未完成或 Go 基线失败 | 暂停本计划施工，先完成/修复骨架；记录原因，不通过重建工程绕过 |
| 其他会话仍有未提交后端修改 | 只读确认并在协调后施工，不覆盖、不清理对方文件 |
| 现有骨架与架构契约不一致 | 先记录差异和用户影响，在现有分层内修正；不保留两套接口兼容垃圾 |
| SQLite 驱动连接配置与预期不同 | 以已锁定驱动文档和实测为准，记录实际参数；不擅自更换驱动 |
| 端口或正式数据库被占用 | 使用独立临时端口和数据库，不终止其他进程、不删除数据 |
| 时间同秒导致 updatedAt 字符串不变 | 按秒级 RFC 3339 约定接受；验证更新结果和持久化，不伪造纳秒或人为加一秒 |
| 无法完成真实重启 | 不将存储重连测试等同于完整 AC-10；把进程重启列为未验证并保留明确手工步骤 |
| 发现计划外问题 | 记录施工日志，不顺手扩展 Unity、React 或加分功能 |

允许在发现方案有技术破绽时调整实现，但必须在施工日志和提交信息（如发生提交）写明原方案问题、新方案理由和影响，不能沉默改变 API 契约。
