# 复盘 002：AR 虚拟内容偏移与相机位姿冻结

- 日期：2026-10-28
- 影响范围：计划 004 的 Unity 真机平面可视化、点击放置与标记跟随显示；HTTP 上报与后端数据保存不受此问题直接影响
- 当前状态：**已修复并通过真机复验**（2026-10-28 计划 005）。AR 输入管理器补齐、Input System 姿态驱动按官方绑定、初始化/搭建同源、精确门禁与负例测试；真机证据：139 条姿态采样零冻结、24 组放置标记投影与触点偏移 0px、世界锁定与平面对齐通过、上报与 UI 回归通过。详见 `docs/evidence/005-unity-camera-pose-fix/verification-report.md`
- 一句话结论：ARCore 会话、平面检测和射线命中持续工作，但 Unity 渲染相机没有收到手机的位置与旋转；正确的空间坐标被冻结的相机投影到了错误位置，而不是射线或标记坐标本身算错。补齐 AR Session 的 ARInputManager 并将主相机换成 Input System 版 TrackedPoseDriver（手持 AR 设备绑定）后，设备姿态进入渲染相机，偏移消失。

## 1. 问题现象

真机上可以识别平面并执行放置，但虚拟内容与相机拍摄的真实环境不能对齐：

1. 蓝色平面轮廓与真实桌面相似，显示位置却明显偏低，甚至大部分位于屏幕外。
2. 点击已检出的平面后，黄色标记经常出现在触点下方或屏幕外。
3. 标记出屏时，上报按钮也随之消失。按钮本身按屏幕投影跟随并在出屏时隐藏，这不是独立的按钮显示故障。
4. 平面、标记与按钮在虚拟渲染层内部能够相互对应，但它们共同与真实相机画面错位。

在 Vulkan 切换为 OpenGL ES 3 后，偏移仍然存在；因此不能把问题归因于某一种图形接口。

## 2. 诊断依据

开发构建在每次成功附锚放置后，等待该帧渲染结束，保存一张现场截图和一份结构化记录。记录包括触点、命中点、平面边界、标记投影、相机姿态、投影矩阵、会话状态等信息。截图只保存在手机应用目录，不自动上传。

本次分析使用两个排查会话共同读取的五组真机记录，时间范围为 03:33:14～03:34:29，约 75 秒。

| 观察项 | 五组记录的事实 | 能说明什么 |
| --- | --- | --- |
| 相机位置 | 始终为 `(0, 1.1176, 0)`，没有变化 | Unity 渲染相机没有跟随手机平移 |
| 相机旋转 | 始终为单位旋转，正方向始终不变 | Unity 渲染相机没有跟随手机转动 |
| 世界到相机矩阵 | 五组数据完全一致 | 用于绘制虚拟内容的相机姿态被冻结 |
| AR 会话与平面 | 会话保持正常跟踪，检出平面由 1 个增加到 5 个 | ARCore 并未整体停止工作，平面数据仍在更新 |
| 命中与标记世界坐标 | 每次放置的标记位置与射线命中位置一致 | 标记实例化和附锚没有额外增加位置偏移 |
| 标记屏幕投影 | 多次位于触点下方，且落在屏幕外 | 虚拟内容出屏可由冻结相机重新投影解释 |

记录中的相机高度还与场景默认相机偏移一致，进一步说明相机停留在初始姿态。

平面增多本身不能单独证明手机一定在移动；结论依据的是真机操作过程、持续变化的 AR 数据与始终不变的相机姿态共同构成的矛盾。

## 3. 根因：设备姿态没有进入渲染相机

当前 AR Foundation / ARCore 版本为 6.6.2。手持 AR 设备通过 Input System 提供设备位置和旋转，官方场景创建逻辑也使用 Input System 版姿态驱动接收这两路数据。

当前工程却存在两处相互关联的问题：

1. **主相机使用旧版空间跟踪姿态驱动。** 它沿旧式设备姿态通道取数据，与当前手持 AR 输入链路不匹配，实际运行中没有更新相机姿态。
2. **AR Session 缺少配套的 AR 输入管理器。** 官方创建 AR Session 时会同时添加会话与输入管理器；当前场景只创建了前者，手持 AR 输入链路不完整。

工程初始化工具是问题进入场景的来源：它优先查找的旧版 AR 姿态组件在当前 AR Foundation 中已弃用，查找失败后回退为旧式空间跟踪驱动。因此，仅手动修改当前场景还不够，初始化工具和场景需要一起修正，避免重新初始化后问题复发。

## 4. 为什么相机实景正常，虚拟内容仍会错位

相机背景画面与 Unity 相机姿态是两条不同的链路：

- 相机背景组件可以把手机实拍画面绘制到屏幕上；
- 平面、标记等虚拟物体则依赖 Unity 相机的位置、旋转和投影矩阵进行绘制。

所以，**实拍画面清晰流畅，不代表虚拟相机正在跟随手机。** 当前现象正是背景链路可用、虚拟相机姿态链路失效。

同理，平面投影与标记在截图中互相对得上，只能证明“平面数据—冻结相机—投影—虚拟渲染”内部一致，不能证明它们与真实世界对齐。两个排查会话正是据此排除了“渲染自洽，所以只剩射线有误”的推断。

## 5. 已排除的解释

| 曾怀疑的方向 | 复核结果 | 后续处理原则 |
| --- | --- | --- |
| 屏幕触点转射线存在约 30～40° 映射错误 | 该角度对应手机真实俯视角度；冻结相机足以解释正确的世界命中点为何投影到屏幕外 | 不修改射线算法，不对触点或命中坐标增加补偿 |
| 投影矩阵与相机内参宽高比错配 | 矩阵两轴参数之比约为 2.2219，与显示比例 2400/1080 一致；反推竖直视场角约 67.026°，与记录一致 | 不修改投影矩阵；相机图像内参与屏幕显示尺寸不同不是天然错误 |
| 同一平面漂移约 0.8 米 | 前三次命中同一平面，后两次命中的是不同平面，不能把不同平面的位置变化当作同一平面漂移 | 区分平面身份后再判断漂移，不以坐标差直接归因 |
| 锚点或标记实例化带来额外偏移 | 每次标记世界坐标与对应命中世界坐标一致 | 保持现有附锚放置模型，优先修相机输入 |
| Vulkan 导致显示映射错误 | 强制 OpenGL ES 3 后问题仍出现 | 不再以切换图形接口作为该问题的修复方向 |
| 手机算力或 ARCore 不可用 | 设备已通过 ARCore 会话与跟踪验证，本次会话持续正常，且存在明确的相机输入断链证据 | 性能问题单独处理，不与空间对齐问题混为一谈 |

之前的“距离过远”和“位于相机后方”判断也依赖相机姿态。在相机冻结时，它们可能误拒绝正常命中或放行异常命中，不能作为独立证据证明平面本身异常。

## 6. 为什么编辑器测试没有提前发现

编辑器中的 AR 模拟有独立的模拟相机姿态来源，可以驱动相机移动，因此不会自然复现真机手持 AR 输入未接通的问题。

现有投影和放置测试也不能替代真机姿态验证：如果测试与渲染共同使用同一个冻结相机，计算结果仍可能内部一致。阶段门禁通过代表工程配置、接线和算法契约通过，不代表真机的设备姿态已经进入相机。

## 7. 修复方向与验收标准

以下方向已于 2026-10-28 按计划 005 实施（AR 输入管理器、Input System 姿态驱动与官方绑定、初始化/搭建同源、精确门禁与负例测试；实施细节与证据见计划 005 施工日志）；下列验收标准仍待真机执行，真机通过前本问题不关闭：

1. 在 AR Session 所在对象补齐 AR 输入管理器。
2. 主相机只保留一个 Input System 版姿态驱动，按当前 AR Foundation 官方创建逻辑绑定手持 AR 设备的位置与旋转；不叠加旧驱动，也不退回已弃用的 AR 姿态组件。
3. 同步修改工程初始化工具，并为输入管理器、驱动类型和手持 AR 输入绑定增加场景自检。
4. 不先放宽现有放置距离与前方校验。先恢复真实相机姿态，再根据新真机记录判断这些校验是否合理。
5. 不采用固定角度、固定像素或坐标偏移补偿。此类补偿会掩盖根因，并随持机姿势变化再次失效。

修复后必须同时满足：

1. 手机移动、转动时，诊断记录中的相机位置与旋转随之变化。
2. 重新扫描并点击平面后，命中点与标记投影回到触点附近，标记正常可见。
3. 移动和绕动手机时，蓝色平面贴合真实表面，标记保持在原真实位置，而非随手机视角一起漂移。
4. 上报按钮正常跟随，表单与设置面板操作不会误触发放置。
5. 重新完成一次真实 HTTP 上报，确认三端字段与保存结果未受修复影响。
6. 编辑器模拟仍能运行，避免真机修复破坏现有模拟验证。

## 8. 防再犯规则

1. **AR 验收必须分别验证背景、设备姿态和空间内容。** 相机有画面、会话正在跟踪、平面数量增加，都不能替代相机姿态随真实设备变化的检查。
2. **虚拟渲染内部自洽不等于真实世界对齐。** 需要把同一世界点、触点、屏幕投影和真实截图放在一起判断。
3. **先比较跨时间的原始数据，再提出补偿算法。** 本例中“姿态完全不变”是比视觉偏移更直接的诊断信号。
4. **手工场景与初始化工具必须同源。** 修场景而不修生成逻辑，会在下次初始化时重新引入缺陷。
5. **依赖包升级后核对官方场景创建方式。** 不应通过类型查找失败后的静默回退维持一个已经改变输入机制的组件配置。

## 10. 修复与真机验证结论（2026-10-28 计划 005 追加）

第 7 节方向已全部实施并通过真机验收，本问题关闭。关键事实：

1. **修复内容**：AR Session 同对象唯一 ARInputManager；主相机唯一 `UnityEngine.InputSystem.XR.TrackedPoseDriver`，按 AR Foundation 6.6.2 官方 `XROriginCreateUtil.CreateARMainCamera` 绑定 `<XRHMD>/centerEye*` + `<HandheldARInputDevice>/device*`；旧版 SpatialTracking 驱动删除；`ProjectSetup.EnsureArcameraInput` 统一初始化与搭建配置；门禁升级为精确检查（35/35）+ 5 个 EditMode 测试含负例（31/31）。
2. **真机证据**（iQOO Z9，新版安装 05:41:22）：相机姿态采样 139 条、跟踪后最长完全一致连续段 1 条（修复前全程冻结）；24 组放置标记世界坐标=命中点、投影-触点偏移 0px、全部在屏内；世界锁定 19 秒段标记坐标漂移 ≤0.03 m（锚点微调）而相机持续运动；蓝色平面贴地。
3. **业务回归**：UI 防误触、跟随按钮、上报成功（独立临时后端，坐标与状态正确）、失败中文提示与草稿保留、恢复重试、地址重启保留全部通过；2 米/前方校验未改动。
4. **遗留观察项**（不属本问题）：门/柜附近偶发小片伪平面（ARCore 检测质量）；后台/息屏相机恢复仍是独立已知问题，未在本期修复。
5. **过程教训补充**：真机自动化验证中 adb `input tap` 坐标原点在左上、Unity 触摸原点在左下，必须做 y 轴换算；虚拟键盘「返回」可能回退输入，应用「确定/回车」提交后再操作保存按钮。
